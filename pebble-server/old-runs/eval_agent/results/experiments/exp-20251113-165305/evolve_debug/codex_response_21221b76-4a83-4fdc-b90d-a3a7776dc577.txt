**Behavior & Performance**
- 50 k rps saw overall p99 fall to 5.832 ms (parent: 7.168 ms) while the client kept only single-digit outstanding requests even though just workers 0‑3 logged traffic, so throughput effectively matched the offered rate (results/experiments/exp-20251113-165305/summary.json:31; results/experiments/exp-20251113-164205/summary.json:31; results/run-20251113-165305/logs/client.log:2; results/run-20251113-165305/logs/server/server.log:4).
- At 60 k rps the whitening step removed the prior low-index bias—p99 shrank from 2.59 s to 26 ms despite only workers 1‑3 being used, and the client log shows the queue draining every second (results/experiments/exp-20251113-165305/summary.json:51; results/experiments/exp-20251113-164205/summary.json:51; results/run-20251113-165325/logs/server/server.log:4; results/run-20251113-165325/logs/client.log:2).
- 80 k rps regressed: the server emitted just ~57–72 k responses/sec because traffic still hit only four sockets (0/1/2/5), so each worker spent long stretches in the 10 µs/2 ms busy-wait handlers and queueing drove p99 to 2.63 s with 23 k replies missing (results/experiments/exp-20251113-165305/summary.json:70; results/run-20251113-165345/logs/server/server.log:4; results/run-20251113-165345/logs/server/server.log:8; results/run-20251113-165345/logs/client.log:17; internal/server/server.go:286; internal/server/server.go:313).
- 100 k and 140 k rps collapsed even further—p99 jumped to 4.5 s and 6.4 s versus the parent’s 0.66 s and 3.8 s because only four workers carried ~80–93 k rps, leaving 111 k and 356 k outstanding requests that never came back (results/experiments/exp-20251113-165305/summary.json:90; results/experiments/exp-20251113-165305/summary.json:110; results/experiments/exp-20251113-164205/summary.json:90; results/experiments/exp-20251113-164205/summary.json:110; results/run-20251113-165405/logs/server/server.log:4; results/run-20251113-165405/logs/server/server.log:8; results/run-20251113-165424/logs/server/server.log:4; results/run-20251113-165424/logs/server/server.log:8; results/run-20251113-165405/logs/client.log:17; results/run-20251113-165424/logs/client.log:17).
- Confidence: **Medium**—the logs clearly show under-utilized sockets and accumulating backlogs, but we cannot see why the selector never activates the remaining two reuseport targets.

**Program Intent**
- The selector’s stated intent is to whiten `reuse->hash` with a Murmur3 fmix, then pick exactly one slot via bitmask/multiply-high so requests spread evenly with minimal instructions (ebpf/agent.c:41; ebpf/agent.c:73; ebpf/agent.c:81; ebpf/agent.c:89).
- The Go server programs the agent state with all six worker FDs, so the policy expects every reuseport socket to participate (internal/server/ebpf.go:103; internal/server/ebpf.go:124).
- In practice the behavior only matches that intent at ≤60 k rps; at ≥80 k rps the selector still feeds only four sockets, causing multi-second p99s and large response loss, so the fairness/latency goals are not achieved (results/experiments/exp-20251113-165305/summary.json:70; results/experiments/exp-20251113-164205/summary.json:90; results/run-20251113-165345/logs/server/server.log:4; results/run-20251113-165405/logs/client.log:17).
