**Behavior & Performance**  
- Load sweep stayed healthy only up to 80 k req/s: p99 latencies were 6.5 ms (50 k), 15.9 ms (60 k), and 9.9 ms (80 k), roughly comparable to the parent (5.1/18.8/11.7 ms). When the send rate rose to 100 k, p99 exploded to 6.4 s with 374 k replies missing, and 140 k held at ~3.9 s while still dropping 160 k replies (metrics table plus `results/run-20251113-171348` and `results/run-20251113-171405` client logs showing outstanding ≥4×10^5).  
- Server logs reveal that only a subset of the six sockets ever handled traffic: at 50 k only workers 0,3,4,5 carried ~49 k req/s, workers 1–2 were idle (`results/run-20251113-171248/server.log` 17:12:55). The skew worsened with load; at 100 k essentially only workers 3–4 processed requests (≈52 k req/s total, `results/run-20251113-171348/server.log` 17:13:54–17:14:05), capping throughput far below the offered rate and causing the queue blow-up observed by the client.  
- The new selector never actually performs the intended length split: its only branch (`reuse->len > 64`) is never true because both GET and SCAN payloads are <50 B (`cmd/workload_client/main.go:340-380`), so every packet follows the “base slot” path in `ebpf/agent.c:1-70`. That reduces the policy to a single `bpf_sk_select_reuseport` keyed solely by `reuse->hash`, which pins each client flow to one socket and leaves the unused sockets idle whenever there are hash collisions among the seven client senders.  
- With 99 % GET traffic mapped onto just two sockets at 100 k+, those workers hit their busy-wait delays back-to-back, backlog grows by ~50 k per second, and client-reported p99 reflects queueing delay rather than server processing time. SCAN isolation and tail reduction therefore never materialize, while overall throughput collapses versus the parent (0.64 s vs 6.4 s p99 at 100 k).  
- **Confidence:** Medium (behavior is well evidenced by logs, but the exact hash distribution inside the kernel is inferred).

**Program Intent vs. Reality**  
- Intent (per `ebpf/agent.c` comments) was to “steer larger packets (likely SCANs) to the upper half of sockets” so heavy scans stay off the GET-heavy sockets while keeping a single cheap selection call.  
- Failure: because the workload never produces packets above 64 B, the “upper half” path never executes, so scans and gets share the same few sockets. Worker logs and the massive p99 spike at ≥100 k req/s show that the system neither balanced load nor isolated heavy requests; instead it achieved less concurrency than the parent (only two sockets active under stress) and vastly worse tail latency and loss.

**Missing Signals & New Metrics/Logs**  
- **What:** Actual packet-length histogram per workload phase. **How:** have the client log the min/median/max payload sizes it sends (already knows request strings); extremely low overhead. **Why:** would have exposed immediately that no request ever crosses the 64 B threshold, invalidating the eBPF split assumption before deployment.  
- **What:** Per-slot selection counters (e.g., BPF per-CPU array incremented by slot index, exported once per second). **How:** add a tiny array map the selector bumps before `bpf_sk_select_reuseport`, and have the Go server scrape/report it alongside the worker stats. **Why:** would quantify how many sockets are actually chosen, letting us confirm hash collisions or misconfiguration without inferring from indirect throughput symptoms.
